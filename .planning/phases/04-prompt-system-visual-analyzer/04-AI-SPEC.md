## 1. System Classification

**System Type:** Content Generation Pipeline (含 Visual Analyzer)

**Description:**
此系统为 Rust 库（narratoai-core）的两个子模块：Prompt 系统（版本化模板注册表 + regex `${variable}` 渲染 + 输出验证）和 Visual Analyzer（FFmpeg 帧提取 → 批量编码 → 通过 async-openai 调用视觉 LLM → JSON 结构化分析报告）。调用方为 Phase 6 Documentary Pipeline。不面向终端用户，是内部基础设施组件。

**Critical Failure Modes:**
1. 模板渲染遗漏变量导致 LLM 收到不完整 prompt，产生不可预测的输出格式
2. 帧提取失败时静默跳过导致分析报告帧数不完整，下游脚本生成不准确
3. 批量视觉分析中单个批次 JSON 解析失败未报告，丢失一个批次的帧观察数据
4. Semaphore 并发控制失效导致同时发起过多 API 调用，触发限流或超出配额

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** AI-powered video content creation (影视解说 / automated documentary and short-drama narration generation)

**User Population:** Internal infrastructure consumed by Phase 6 Documentary Pipeline (Rust crate `narratoai-core`). End users through the Tauri desktop app are content creators (视频创作者、自媒体运营者) who generate AI-narrated videos. This phase's direct consumers are pipeline integrators (下游流水线开发者) who call `prompt::render_template()` and `visual::analyze_video_frames()`.

**Stakes Level:** Medium

**Output Consequence:** The Visual Analyzer produces structured JSON frame observations (`FrameObservation` + `BatchAnalysisResult`) that are the sole visual input to Phase 6 narration script generation. If the JSON report is missing frames, hallucinates scene details, or produces untrustworthy observations, the downstream LLM will generate a narration script that visually contradicts the video content — resulting in nonsensical output that users will reject (wasted API cost, user time, and eroded trust in the tool). For the Prompt system, incorrect template rendering causes the downstream LLM to receive broken instructions, producing unpredictable output formats.

### What Domain Experts Evaluate Against

```
Dimension: 场景覆盖完整性 (Scene Coverage Completeness)
Good (domain expert would accept): 帧序列覆盖了视频中所有明显场景切换点——每个场景至少有一个代表帧被分析，帧间间隔不会跳过关键情节时间点（如标题卡、快速剪辑切换点）
Bad (domain expert would flag): 某一幕场景的所有帧被完全跳过导致下游未生成对应解说文案；80%的分析帧集中在视频前段，后1/3完全没有帧被分析
Stakes: High
Source: KFS-Bench (NEC 2025) — Scene Hit Rate (SHR) 被证明与下游QA准确率直接相关；均匀采样导致>90%关键内容被遗漏 (AAAI 2026)
```

```
Dimension: 画面观察忠实度 (Visual Observation Faithfulness)
Good (domain expert would accept): 每帧的 scene_description 描述的是画面中实际可见的内容（"一个穿蓝色西装的男子站在讲台后，麦克风在面前，背景是红色幕布"），object list 包含画面中可识别的具体对象
Bad (domain expert would flag): 描述使用了通用填充语（"一个人正在说话"、"一个场景正在发生"），可套用到任何帧；object list 为空或仅含1-2个泛化项；描述中出现画面中不可见的内容
Stakes: High
Source: VBenchComp (Apple 2025) — VLLM 依赖语言先验而非实际视觉内容的"shuffling invariance"问题；AAAI 2026 — 视觉编码器-解码器断连导致文本先验压制视觉信号
```

```

Good (domain expert would accept): 每个批次的 LLM 返回都能被 serde_json::from_str<FrameObservation> 成功解析，所有必须字段(frame_number/timestamp/scene_description/objects/actions)均存在且类型正确，无明显多余字段或 markdown 代码块包裹

Stakes: Critical

```

```
Dimension: 跨帧时间连贯性 (Cross-Frame Temporal Coherence)
Good (domain expert would accept): 同一场景的连续帧之间的对象列表保持一致（"桌上的咖啡杯"不会在下一帧消失又出现）；场景描述不会在相邻帧中自相矛盾（不会上一帧说"室内"，下一帧同场景说"室外"）
Bad (domain expert would flag): 相邻帧的描述中存在矛盾信息；同一场景内的 objects 列表随机变化；人物/物体在几帧间隔内"闪现"而没有合理过渡
Stakes: Medium
Source: iMerit (2025) — AI 生成视频的 temporal drift 分析，跨帧对象一致性是核心质量维度；Video-MME-v2 (NJU+Google 2026) — 时序理解作为三级能力框架的第二层
```

```

Good (domain expert would accept): scene_description 包含 3-5 句具体观察（场景设定、光线、构图、人物动作、表情）；objects 列表 3-8 个具体项目；on_screen_text 在出现字幕/标题卡时有完整提取

### Known Failure Modes in This Domain

1. **关键帧采样遗漏情节节点** — 固定间隔采样（如每3秒一帧）会错过短暂但关键的事件：标题卡持续仅0.5秒、快速镜头切换、关键剧情转折镜头。AAAI 2026 研究表明均匀采样遗漏了超过90%的关键内容。本系统虽有4级回退策略确保提取成功，但未解决"帧选得对不对"的语义覆盖问题——可能成功提取了200帧但它们都来自同一个场景。

2. **视觉 LLM 默认输出通用描述** — 当帧画面模糊、过暗或内容复杂时，视觉 LLM 倾向于退回"常识"文本先验而非承认不确定性。表现为：生成听起来合理但与画面实际内容不符的场景描述（VBenchComp 语言先验问题）。本系统的低 temperature (0.1) 策略部分缓解但不能根除。

3. **批量间 JSON schema 偏离** — 不同分析批次可能返回略有不同的 JSON 字段结构（字段名大小写、嵌套深度、可选字段有无）。导致 serde 反序列化在部分批次上失败，数据流入 `BatchAnalysisResult.errors`。SO-Bench 将此记录为多模态 LLM 的已知结构化输出问题。本系统的 D-14（收集错误继续执行）策略容忍此问题而非解决它。

4. **跨场景批次污染** — 单个 batch（10帧）可能跨越多个不同画面场景。LLM 在同时看到 A 场景和 B 场景的帧后，其 "overall_activity_summary" 的描述可能将两个场景的特征错误合并，产生混淆的分析。

## 2. Framework Decision

**Selected Framework:** async-openai v0.36 + 自实现 regex 模板引擎 + ffmpeg-sidecar v2.5.1

**Version:** async-openai 0.36, ffmpeg-sidecar 2.5.1

**Rationale:**
项目为纯 Rust 库，传统 Python AI 框架（LangChain/CrewAI/LlamaIndex）完全不适用。async-openai v0.36 提供成熟的 OpenAI 兼容协议客户端，Phase 2 已封装为 `LlmProvider` trait（含 `analyze_images()` 方法）。自实现 regex 模板引擎（D-05）确保 `${variable}` 语法与 Python 版完全兼容，模板迁移零修改——minijinja/tera/handlebars 均使用 `{{ }}` 语法，全部需要改写模板。ffmpeg-sidecar 帧提取（D-09 至 D-12）对齐 Python 版 4 级回退策略，Rust 原生视频库（video-rs、rav1e）不支持同等回退。三个选择均在 CONTEXT.md 24 项决策中锁定并验证。

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| minijinja / tera / handlebars | 使用 `{{ }}` 语法，与 Python 版 `${variable}` 不兼容，模板需全部改写 |
| reqwest 直接调用 | 需手写 SSE 解析/重试/限流/错误处理，Phase 2 async-openai 已完成此工作 |
| video-rs / rav1e | 不支持完整 4 级回退策略（硬件加速→软件→PNG→BMP） |
| candle / ort / tract | 本地模型推理框架，非 LLM API 客户端，不适用 |
| llm_client | 社区极小，不支持流式/视觉模型 |

**Vendor Lock-In Accepted:** Partial — OpenAI 兼容协议理论上可接入任何兼容端点（DeepSeek、Gemini 等），但 async-openai 依赖 OpenAI API 规范演进

### Entry Point Pattern

以下为 Phase 4 核心流水线的 Rust 入口模式：Prompt 渲染 → 帧提取 → 批量视觉分析。

```rust
use std::collections::HashMap;
use std::path::Path;
use std::sync::Arc;
use regex::Regex;
use tokio::sync::Semaphore;
use tracing::{info, error};

/// 模板渲染：将 ${variable} 和 $variable 替换为上下文值
fn render_template(template: &str, vars: &HashMap<&str, &str>) -> Result<String, PromptError> {
    let re = Regex::new(r"\$\{(\w+)\}|\$(\w+)").map_err(|e| {
        PromptError::TemplateRender(format!("正则编译失败: {}", e))
    })?;

    let result = re.replace_all(template, |caps: &regex::Captures| {
        let name = caps.get(1).or_else(|| caps.get(2))
            .map(|m| m.as_str())
            .unwrap_or("");
        vars.get(name).copied().unwrap_or_else(|| {
            // D-07: 缺失变量返回错误
            // 但在闭包中无法直接返回 Result，通过标记 panicking sentinel
            // 实际实现用 find_iter + 预校验替代
            ""
        })
    });

    Ok(result.to_string())
}

/// 视觉分析入口：帧提取 + 批量 LLM 分析 + JSON 报告
async fn analyze_video_frames(
    video_path: &Path,
    llm_provider: &dyn LlmProvider,
    prompt_template: &str,
    context: &HashMap<&str, &str>,
    batch_size: usize,
    max_concurrency: usize,
    progress: Option<ProgressCallback>,
) -> Result<BatchAnalysisResult, VisualError> {
    // Step 1: 提取关键帧（spawn_blocking + ffmpeg-sidecar）
    let frame_dir = std::env::temp_dir().join("narratoai_frames");
    let frame_count = extract_frames(video_path, &frame_dir, 3.0, None, progress.clone())
        .await
        .map_err(VisualError::FrameExtraction)?;

    if frame_count == 0 {
        return Err(VisualError::FrameExtraction("未提取到任何帧".into()));
    }

    // Step 2: 渲染 Prompt 模板
    let rendered_prompt = render_template(prompt_template, context)
        .map_err(|e| VisualError::Analysis(format!("Prompt 渲染失败: {}", e)))?;

    // Step 3: 收集帧文件路径
    let mut frame_paths: Vec<std::path::PathBuf> = std::fs::read_dir(&frame_dir)
        .map_err(|e| VisualError::FrameExtraction(format!("读取帧目录失败: {}", e)))?
        .filter_map(|entry| entry.ok())
        .map(|e| e.path())
        .filter(|p| p.extension().and_then(|s| s.to_str()) == Some("jpg"))
        .collect();
    frame_paths.sort();

    if frame_paths.is_empty() {
        return Err(VisualError::Analysis("没有可分析的帧".into()));
    }

    // Step 4: 通过 LlmProvider analyze_images 批量发送
    let results = llm_provider
        .analyze_images(
            &frame_paths,
            &rendered_prompt,
            None,               // system_prompt
            Some(batch_size),   // batch_size
            Some(max_concurrency),
            Some(LlmResponseFormat::Json),
            Some(0.1),          // temperature
            Some(4096),         // max_tokens
        )
        .await
        .map_err(|e| VisualError::Analysis(format!("LLM 分析失败: {}", e)))?;

    // Step 5: 反序列化 JSON 结构
    let mut observations = Vec::new();
    let mut errors: Vec<String> = Vec::new();

    for (idx, json_text) in results.iter().enumerate() {
        match serde_json::from_str::<FrameObservation>(json_text) {
            Ok(obs) => observations.push(obs),
            Err(e) => {
                let err_msg = format!("批次 {} JSON 解析失败: {}", idx, e);
                error!("{}", err_msg);
                errors.push(err_msg);
                // D-14: 收集错误继续执行
            }
        }
    }

    if observations.is_empty() && !errors.is_empty() {
        return Err(VisualError::BatchPartial {
            analyzed_count: 0,
            total_count: results.len(),
            errors,
        });
    }

    if let Some(ref cb) = progress {
        (cb)(Some(1.0), "视觉分析完成");
    }

    Ok(BatchAnalysisResult {
        observations,
        total_frames: frame_count as usize,
        analyzed_batches: results.len(),
        errors,
    })
}
```

### Common Pitfalls

1. **async-openai builder API 不自动处理空 response_format 字段** — 当不需要 JSON 模式时，必须在 builder 上**省略**`.response_format()` 调用，而非传入 `None`。builder setter 接收 `ResponseFormat` 而非 `Option<ResponseFormat>`，类型系统不会阻止你设置一个 "不同" 的值。Phase 2 代码通过 `if use_json { request_builder.response_format(ResponseFormat::JsonObject); }` 条件调用规避此问题。如果直接调用 `.response_format(value)` 传入默认值 会在请求体中包含 `response_format: null`，某些网关（如硅基流动）会返回 400 错误。

2. **`regex::Regex::replace_all` 闭包内无法返回 Result** — 当需要在替换闭包中报告错误（如模板变量缺失）时，闭包的签名要求返回 `&str` 或 `String`，不支持 `Result<String, Error>`。解决方案（D-07 决定的模式）：渲染前先通过 `find_iter()` 提取所有变量名并与上下文比对，确保变量全部存在后再执行 `replace_all`。或者将缺失变量替换为特殊 sentinel 字符串并在之后检查。

3. **ffmpeg-sidecar 的 `spawn()` 是同步阻塞的** — `FfmpegCommand::spawn()` 调用 `std::process::Command::spawn()`，在同步上下文中返回。如果在 Tokio 异步上下文中直接调用会短暂阻塞 worker 线程。必须使用 `tokio::task::spawn_blocking()` 包装整个 FFmpeg 生命周期（spawn → iter → wait）。Phase 1 中的 `run_ffmpeg()` 函数已封装此模式。

4. **`Semaphore` 的 `acquire_owned()` 在 tokio::spawn 闭包中需 `Send`** — `SemaphorePermit` 是 `Send` 但不是 `Sync`，在 `.await` 点之间持有 permit 是安全的。但如果在 `tokio::spawn(async move { ... })` 中获取 permit 并在 `.await` 之间传递，需要确保 permit 在闭包中合理持有。推荐在每个 tokio::spawn 内获取 permit 并在使用后自动 drop（离开作用域），而非在 spawn 外集中获取。

5. **serde_json `from_str` 遇到 LLM 返回 markdown 代码块会失败** — 即使设置了 `response_format=json_object`，某些模型仍会返回 `\`\`\`json\n{...}\n\`\`\``。`serde_json::from_str()` 无法解析代码块包裹的 JSON。需要先检查并剥离 markdown 代码块标记。Phase 2 的 JSON 回退逻辑已在 prompt 中追加约束，但视觉分析代码仍应做防御性剥离：`text.trim().strip_prefix("```json").or(...)`。

### State Management

**Prompt 系统** — 全局注册表模式（D-18）：

**视觉分析器** — 无状态设计：

- `extract_frames()` 是有状态操作（需要 `output_dir` 参数），但状态由调用方管理（D-23）

- 进度回调通过 `Option<ProgressCallback>` 参数传入和上报（D-16）

### Context Window Strategy

视觉分析处理的是图片帧而非长文本，上下文窗口管理策略如下：

**帧数量管理：**
- 按 `batch_size`（默认 10）分组发送，每组包含 prompt 文本 + 10 张 base64 data URL（每张约 100-300KB）
- `batch_size` 不应大于 15，超过会导致单请求 payload 过大（> 5MB）以及视觉 LLM 注意力分散
- 总帧数控制：如果视频过长导致帧数过多（例：30 分钟视频 @ 3 秒间隔 = 600 帧），只选择前 N 帧或均匀采样
- 均匀采样通过动态调整间隔实现：`interval = duration / max_frames`

**LLM 上下文窗口限制：**
- 视觉模型上下文窗口（例：GPT-4o 128K tokens）限制的是文本 tokens 而非图片 tokens
- 图片消耗的 tokens 按图片尺寸计算（GPT-4o: 每张 1024x1024 约 255 tokens at low detail）
- 单批次 10 张 1024px 图片约消耗 2550 tokens + prompt 文本，远低于 128K 窗口
- 注意：部分模型对输入图片数量有限制（如 GPT-4o 支持多张但 Qwen-VL 最多 20 张）

**Prompt 长度管理：**
- 帧分析 prompt 通常较短（200-500 tokens），无需 truncation
- 输出 JSON 通过 `response_format=json_object` 限制格式，max_tokens=4096 留够余量
- 不需要 RAG 式的 chunking/reranking

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with serde

在 Rust 项目中，"Pydantic" 的等价物是 **serde** + **serde_json**。使用 `#[derive(Deserialize)]` 定义输出 schema，由 LLM 返回 JSON 后反序列化验证。

**帧分析输出模型（对应 D-15: FrameObservation + BatchAnalysisResult）：**

```rust
use serde::{Deserialize, Serialize};

/// 单帧观察结果（对齐 Python 版 frame_observation 字典）
#[derive(Debug, Clone, Deserialize, Serialize)]
#[serde(deny_unknown_fields)]  // 拒绝未知字段，防止 LLM 额外添加非约定字段
pub struct FrameObservation {
    /// 帧序号（从 0 开始）
    pub frame_number: u64,
    /// 帧时间码（格式: HH:MM:SS.mmm）
    pub timestamp: String,
    /// 场景描述
    pub scene_description: String,
    /// 检测到的物体/人物列表
    pub objects: Vec<String>,
    /// 画面动作/行为描述
    pub actions: Vec<String>,
    /// 字幕/文字内容（如果有）
    pub on_screen_text: Option<String>,
    /// 视觉显著性评分 0.0-1.0
    pub visual_salience: Option<f64>,
}

/// 批次分析结果（对齐 Python 版 frame_batch_result）
#[derive(Debug, Clone, Deserialize, Serialize)]
pub struct BatchAnalysisResult {
    /// 帧观察列表
    pub observations: Vec<FrameObservation>,
    /// 总体活动摘要（跨帧的综合分析）
    pub overall_activity_summary: Option<String>,
    /// 元信息
    pub total_frames: usize,
    pub analyzed_batches: usize,
    pub errors: Vec<String>,
}
```

**框架集成方式：**

在 Rust/async-openai 中没有 Python 框架的 `.with_structured_output()` 语法。集成方式为调用级：

| 方式 | 使用场景 | 实现 |
|------|---------|------|
| `response_format=JsonObject` 原生支持 | 大多数 OpenAI 兼容 API | `request_builder.response_format(ResponseFormat::JsonObject)` |
| Prompt 约束回退 | 不支持 `response_format` 的网关 | 在 prompt 末尾追加 JSON 约束，Phase 2 已有 `create_vision_chat_with_json_fallback()` |
| 防御性 JSON 解析 | 所有场景 | 先清理 markdown 代码块，再 `serde_json::from_str()` |

**重试逻辑：**

```rust
/// JSON 反序列化失败时的重试策略
fn parse_and_retry(
    json_text: &str,
    max_attempts: usize,
) -> Result<FrameObservation, VisualError> {
    let mut last_error = None;

    for attempt in 1..=max_attempts {
        // Step 1: 防御性清理 markdown 代码块包裹
        let cleaned = json_text
            .trim()
            .strip_prefix("```json")
            .or_else(|| json_text.trim().strip_prefix("```"))
            .map(|s| s.trim_end_matches("```").trim())
            .unwrap_or(json_text.trim());

        // Step 2: 尝试反序列化
        match serde_json::from_str::<FrameObservation>(cleaned) {
            Ok(obs) => return Ok(obs),
            Err(e) => {
                tracing::warn!(
                    attempt,
                    error = %e,
                    raw_preview = &json_text[..json_text.len().min(200)],
                    "JSON 反序列化失败，尝试次数: {}",
                    attempt
                );
                last_error = Some(e);
                // 仅重试 1 次（= 共 2 次尝试），因为 re-prompt 成本高
                if attempt >= max_attempts {
                    break;
                }
            }
        }
    }

    Err(VisualError::Analysis(format!(
        "JSON 解析失败 ({} 次尝试后放弃): {}",
        max_attempts,
        last_error.as_ref().unwrap()
    )))
}
```

**重试策略要点：**
- 最多重试 1 次（共 2 次尝试），因为重新请求 LLM 的延迟和成本较高
- 第 1 次失败时记录部分原始 JSON（前 200 字符）用于调试
- 连续失败不继续重试——表面错误给调用方（D-14: 收集错误继续执行）
- 错误汇总到 `BatchAnalysisResult.errors` 而非全流水线失败

### Async-First Design

**本框架的 async 机制：**

Rust 项目通过 Tokio 运行时提供 async/await 支持。三个层级：

```
[Tokio Runtime] ← 事件循环，驱动 Future
  ├── async fn (直接在 runtime 上运行，非阻塞)
  ├── tokio::spawn (并发执行 async 任务)
  └── tokio::task::spawn_blocking (包装同步阻塞操作)
```

**Phase 4 中 async 的使用：**

| 操作 | 模式 | 原因 |
|------|------|------|
| LLM API 调用 | 纯 `async` | async-openai 所有方法都是 async，底层使用 reqwest 异步 HTTP |
| FFmpeg 帧提取 | `spawn_blocking` | ffmpeg-sidecar 的 `spawn()` + `iter()` 是同步阻塞的 |
| 图片→base64 编码 | `spawn_blocking` | `image::open()` 是 CPU 密集操作 |
| 模板渲染 | 同步（在 async fn 内 ok） | regex 替换极快（O(n)），微秒级，无需 spawn_blocking |
| Semaphore 控制 | `acquire_owned().await` | 信号量等待是典型的 async 场景 |

**一个常见错误（已在 Phase 1 处理）：**

在 Tokio 异步上下文中用 `std::thread::sleep()` 而不是 `tokio::time::sleep()`。前者会阻塞整个 worker 线程，后者只阻塞当前 task。在 `spawn_blocking` 闭包内使用 `std::thread::sleep()` 则是正确的。

**错误：**
```rust
// 异步函数里使用 std::thread::sleep —— 阻塞整个 worker 线程！
async fn bad_example() {
    std::thread::sleep(Duration::from_secs(1));
}
```

**正确：**
```rust
async fn good_example() {
    tokio::time::sleep(Duration::from_secs(1)).await;
}

// spawn_blocking 内使用 std::thread::sleep 是 OK 的
fn blocking_ffmpeg_task() {
    std::thread::sleep(Duration::from_secs(1));
    // 在阻塞线程上等待 FFmpeg 进程
}
```

**Stream vs. Await：**

- **Stream（流式）**：用于逐 token 返回给调用方（如 TTS 实时播放）。在 Phase 4 中**不使用**——视觉分析是纯批量处理，结果一次性返回即可。
- **Await（非流式）**：用于 `analyze_images()`，等待完整响应后做 serde JSON 校验。验证失败需要重试时，持有完整 text 方便重试。

### Prompt Engineering Discipline

**System/User Prompt 分离：**

视觉分析的 prompt 结构由 `build_vision_messages()` 实现：

**Phase 4 的分层：**
- **框架 Prompt**（硬编码在 `analyzer.rs` 中，对齐 D-19）：JSON 输出格式约束、批量帧处理指令，无需模板化
- **分析 Prompt**（从 Registry 获取，D-19）：文档分析的具体指导（如纪录片帧分析关注场景/物体/文字/色彩），渲染 video_title/language 等变量
- **输出验证 Prompt**（硬编码在 `validators.rs`）：JSON schema 描述、解说文案格式约束

**Few-shot 策略：**

视觉分析使用 **inline few-shot**（放在 prompt 中）而非动态检索：
- 帧分析输出格式固定（JSON schema 在 prompt 中描述），不需要从数据库中检索 few-shot 示例
- 在 prompt 末尾附加 1-2 个 `{"frame_number": 0, "timestamp": "00:00:00.000", ...}` 格式示例
- 示例放在 `\n\nExample output format:\n{...}\n` 段，不带 `\`\`\`` 代码块——避免模型过度模仿

**`max_tokens` 设置：**

| 场景 | max_tokens | 原因 |
|------|-----------|------|
| 帧分析（单帧观察） | 1024 | 单帧 JSON 约 200-500 tokens |
| 帧分析（批量 10 帧） | 4096 | 10 帧 × ~300 tokens + 摘要 |
| 文案生成 | 8192 | 下游 Phase 6，内容更长 |

`max_tokens` 必须始终显式设置。不设置时 async-openai 使用模型默认值（可能非常大，导致成本失控）。

### Context Window Management

**RAG（不适用）：** Phase 4 不涉及文档检索。视觉分析直接从帧文件获取输入。

**视觉分析上下文策略：**

由于处理的是图片而非文本，"context window" 的含义变为图片数量和分辨率：

| 策略 | 实现 | 启用条件 |
|------|------|---------|
| 帧间隔调整 | 动态计算的 interval = duration / max_frames | 帧数量 > max_frames（默认 200） |
| 批处理 | chunks(batch_size) 分组 | 所有场景 |
| 分辨率缩放 | 1024px thumbnail（Phase 2 image_utils） | 所有场景，已在预处理中固定 |
| skip 回退 | 发送失败帧 + 占位符 | D-14: 单帧失败不阻塞其他帧 |

**多帧数量限制：**
- 大多数视觉模型单次请求接受 10-20 张图片
- 超量时图片被压缩或忽略（取决于模型实现，不可控）
- Phase 4 使用 `batch_size=10` 确保每批均在安全范围内
- 帧数量异常多的极端情况：如果 10 分钟视频以 1 秒间隔提取 = 600 帧，会被均匀采样为 ~200 帧

**不使用的模式：** 无 summarisation（视觉分析不需要文本摘要对话）、无 compaction handling（非长时间运行的 agent）。

### Cost and Latency Budget

**单次视觉分析成本估算：**

以 10 分钟视频、3 秒帧间隔 ≈ 200 帧、batch_size=10、20 批为例：

| 模型 | 单价（$/M input tokens） | 每批成本估算 | 200 帧总成本 |
|------|--------------------------|------------|-------------|
| GPT-4o | $2.50 | 文本~100 tokens + 10 张图~2550 tokens = 2650 tokens × $2.50/M = ~$0.0066 | 20 批 = ~$0.13 |
| GPT-4o-mini | $0.15 | 同上 2650 tokens × $0.15/M = ~$0.0004 | 20 批 = ~$0.008 |
| Qwen-VL (硅基流动) | ~$0.40（估计） | ~$0.001 | 20 批 = ~$0.02 |

**输出 tokens 成本（通常为输入价格的 3-10 倍）：**
- 每批输出 ~1500 tokens（10 帧的 JSON），20 批 = 30,000 tokens
- GPT-4o output: 30K × $10/M = ~$0.30
- GPT-4o-mini output: 30K × $0.60/M = ~$0.018

**总成本：** 每次完整视频分析约 $0.03（mini）到 $0.43（4o）。按每天 100 次分析估算：
- GPT-4o-mini: ~$3/天，~$90/月
- GPT-4o: ~$43/天，~$1290/月

**缓存策略：**

| 缓存类型 | 实现 | 命中场景 |
|---------|------|---------|
| 精确匹配缓存 | 以 `(video_path, interval, batch_size)` 为 key 缓存分析结果 | 同一视频多次分析（测试、重试） |
| 语义缓存 | 适用较低级别：模板渲染结果是 pure function 无需缓存 | — |

缓存实现建议：使用 `HashMap<CacheKey, BatchAnalysisResult>` 挂载在 visual 模块的 `OnceLock<Mutex<HashMap>>` 中，仅进程内缓存。Phase 4 阶段不要求持久化缓存。

**子任务模型路由：**

Phase 4 仅一个任务类型（视觉帧分析），无子任务路由。但 Phase 6 Documentary Pipeline 组合使用时可考虑：
- 帧分析 → GPT-4o-mini（成本优先）、GPT-4o（质量优先）——取决于用户配置的 model_name
- 文案生成 → 文本模型（通常在 config.toml `[app]` 段独立配置 text_llm_provider）
- 总结/路由 → 快速便宜模型（如 GPT-4o-mini 或 Gemini Flash）

当前 Phase 4 不实现自动模型路由——由调用方（Phase 6）在请求时指定 provider 实例。

| | | **FAIL:** 描述可套用到任意帧（通用填充语）；`objects` 列表为空或仅含 1 个泛化项；描述中出现画面中不可见但符合语言先验的内容 | | |
| 4 | **模板渲染正确性** (Template Rendering Correctness) | **PASS:** 所有 `${variable}` 和 `$variable` 占位符被正确替换为上下文值；缺失变量返回 `PromptError::TemplateRender` 且明确指出缺失的参数名；6 个过滤器（upper/lower/title/strip/truncate/json）均正确应用；渲染结果与 Python v0.7.8 等价模板的输出逐字符一致 | Code — `assert_eq!` golden file comparison；从 Python 版移植 5 组测试用例，覆盖完整路径+缺失变量+过滤器变体+特殊字符 | High |
| | | **FAIL:** 占位符未被替换（保留 `${xxx}` 原文）；缺失变量返回空字符串而非错误；过滤器应用逻辑错误（如 `upper` 未大写）；与 Python 版输出不一致 | | |
| 5 | **跨帧时间连贯性** (Cross-Frame Temporal Coherence) | **PASS:** 同一场景连续帧间的 `objects` 列表保持语义一致（"桌上咖啡杯"不会在下一帧消失又出现）；相邻帧的场景描述不自相矛盾（"室内"→"室外"仅当存在合理过渡）；同场景相邻帧的对象数量波动不超过 50% | Code (相邻帧对象列表 Jaccard 相似度基线检查，相似度 < 0.2 时标记) + Human review (标记的相邻帧对由审核者判定) | Medium |
| | | **FAIL:** 相邻帧描述存在矛盾信息；同一场景内 objects 列表随机变化（相似度 < 0.2）；人物/物体在无过渡的帧间隔内"闪现" | | |
| 6 | **可用细节密度** (Actionable Detail Density) | **PASS:** `scene_description` 包含 ≥ 3 句具体观察（场景设定、光线、构图、人物动作、表情）；`objects` 列表长度 3-8 个；画面出现字幕/标题卡时 `on_screen_text` 非空 | Code (sentence count via `。！？` 分割、objects.len() 计数) + LLM Judge (描述质量抽样评分：是否包含具体构图/光线/表情信息) | Medium |
| | | **FAIL:** `scene_description` 仅 1 句概括（≤ 1 句）；`objects` 列表为空或仅 1 个泛化项；画面中明显有文字但 `on_screen_text` 为 None | | |
| 7 | **并发控制正确性** (Concurrency Control Correctness) | **PASS:** 给定 `max_concurrency=N`，任何时刻正在执行的 API 请求数不超过 N；单批次失败不影响其他并发批次；Semaphore permit 在请求完成后正确释放（测试中发 N+1 次请求，第 N+1 次等待直到有 permit 释放） | Code — `cargo test` 使用 mock provider（每个模拟请求 hold 200ms），断言同时运行的请求数 ≤ max_concurrency | Medium |
| | | **FAIL:** 同时运行的请求数超过 `max_concurrency`；单个模拟 panic 导致 Semaphore 死锁——后续请求永远无法获取 permit | | |

## 6. Guardrails

### Online (Real-Time)

在线护栏在以下 5 个关键点运行，每个请求必经；且均为 Rust 库内同步/异步检查，无外部依赖，添加的延迟可忽略（微秒到毫秒级）。

| Guardrail | Trigger | Intervention | Location |
|-----------|---------|--------------|----------|
| **模板变量完整性校验** (D-07) | 渲染前 `find_iter()` 发现变量名不在上下文 HashMap 中 | **Block** — 返回 `PromptError::TemplateRender("缺少必需参数: {param_name}")`，明确指出缺失的参数名 | `template.rs::render()` 入口 |
| **帧数量边界检查** | `extract_frames()` 返回 0 帧 | **Block** — 返回 `VisualError::FrameExtraction("未提取到任何帧")`，不继续向 LLM 发送请求 | `analyzer.rs::analyze_video_frames()` step 1 后 |
| **空分析结果屏障** | 所有批次 JSON 解析后 `observations` 为空且 `results` 非空（即有数据但全失败） | **Block** — 返回 `VisualError::BatchPartial { analyzed_count: 0, total_count, errors }`；调用方据此判断是否需要重新分析 | `analyzer.rs::analyze_video_frames()` step 5 后 |
| **JSON markdown 防御剥离** | `serde_json::from_str()` 首次解析失败 | **Flag** — 自动剥离 `\`\`\`json` / `\`\`\`` 包裹并重试；重试日志等级为 `tracing::WARN` | `types.rs::parse_and_retry()` |
| **Semaphore 超时保护** | `acquire_owned()` 等待超过 30 秒（用 `tokio::time::timeout` 包裹） | **Block** — 记录 `tracing::ERROR` 事件，返回 `VisualError::Analysis("并发控制超时")` | `analyzer.rs` Semaphore 获取点 |

### Offline (Flywheel)

离线飞轮通过 Tracing 事件收集质量信号，写入结构化日志。下游（Phase 6 流水线或 Tauri 应用）可汇总这些信号并触发改进循环。

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **JSON 解析失败率** (Critical) | 每次 `parse_and_retry()` 失败时记录 `tracing::WARN`；每批次汇总 errors.count() 写入 `BatchAnalysisResult.errors` | 失败率 > 5%：检查 prompt 中 JSON 格式约束是否充分；增加 few-shot 示例的多样性；验证 `response_format=JsonObject` 是否被模型支持 |
| **场景描述平均句子数** (Medium) | 每次分析后计算 `scene_description` 中 `。！？` 分割的句子数，记录 `tracing::INFO` | 平均值 < 2.5 句：调整 prompt 中详细度约束（如 "请用 3-5 句描述场景设定、光线、构图、人物表情"） |
| **Objects 列表平均长度** (Medium) | 每次分析后计算 `objects.len()` 均值，记录 `tracing::INFO` | 平均值 < 2.5：增加 prompt 中物体示例；检查 `batch_size` 是否过大导致 LLM 注意力稀释（> 10 帧/批时观察力下降） |
| **帧提取回退率** (High) | `extract_frames()` 记录回退路径 vs 快路径的选择，记录 `tracing::INFO` | 回退路径使用率 > 30%：检查 FFmpeg 版本兼容性；验证硬件加速检测逻辑；检查视频编码格式是否在快路径的覆盖范围内 |
| **模板渲染耗时** (Low) | 每次 `render_template()` 计时，记录 `tracing::DEBUG` | 单次 > 100ms：检查模板文件大小（预期 < 10KB）；检查变量数量（预期 < 50 个），排查 regex 回溯问题（预期 O(n) 线性时间） |

## 7. Production Monitoring

**Tracing Tool:** `tracing` crate + `tracing-subscriber` with `env-filter` (结构化日志)

由于本系统是 Rust 库（非服务端应用），监控分两层实现：
1. **库层**：`prompt` 和 `visual` 模块使用 `#[instrument]` 和 `tracing::info!` / `tracing::warn!` / `tracing::error!` 发射结构化事件，附带可查询的 key-value fields。
2. **应用层**：下游调用方（Phase 6 Documentary Pipeline 或 Tauri 命令）初始化 `tracing-subscriber`，选择输出格式（JSON lines 或 human-readable）并决定日志的采集粒度和存储位置。

不使用 Python 生态的 Arize Phoenix —— 它是 Python-only 平台。Rust 的等效方案是 `tracing` + `tracing-subscriber`（均已加入 Cargo.toml，无需额外依赖）。

```rust
// 库内的事件发射模式（prompt/template.rs）
#[instrument(skip(vars))]
pub fn render(template: &str, vars: &HashMap<&str, &str>) -> Result<String, PromptError> {
    let start = std::time::Instant::now();
    let result = /* ... 渲染逻辑 ... */;
    let elapsed = start.elapsed();
    tracing::info!(
        template_len = template.len(),
        var_count = vars.len(),
        elapsed_us = elapsed.as_micros() as u64,
        result_len = /* result length */,
        "template.render.completed"
    );
    result
}

// 库内的事件发射模式（visual/analyzer.rs）
#[instrument(skip_all)]
pub async fn analyze_video_frames(/* ... */) -> Result<BatchAnalysisResult, VisualError> {
    let start = std::time::Instant::now();
    /* ... 分析逻辑 ... */
    let elapsed = start.elapsed();
    tracing::info!(
        frame_count,
        batches,
        observations_count = observations.len(),
        errors_count = errors.len(),
        parse_failures = parse_fail_count,
        elapsed_s = elapsed.as_secs_f64(),
        "visual.analysis.completed"
    );
    if !errors.is_empty() {
        tracing::warn!(
            errors_count = errors.len(),
            total_batches = batches,
            "visual.analysis.partial_errors"
        );
    }
    Ok(BatchAnalysisResult { observations, total_frames: frame_count, analyzed_batches: batches, errors })
}
```

### Key Metrics to Track

| Metric | Source Event Name | Method of Collection | What It Tells You |
|--------|------------------|---------------------|-------------------|
| `template.render.elapsed_us` | `template.render.completed` | `#[instrument]` + `Instant::now()` | Prompt 系统性能基线：正常应 < 200μs；> 1000μs 提示模板过大或 regex 回溯 |
| `frame_extract.count` | 函数返回值 | `extract_frames()` 返回的 `usize` | 帧提取是否正常工作；0 表示 FFmpeg 可能缺失或视频文件损坏 |
| `frame_extract.fallback` | 函数内 tracing INFO | `extract_frames()` 记录是否走了回退路径 | 回退率 > 30% 说明快路径（fps filter）失败过多，应排查 FFmpeg 版本 |
| `visual.analysis.observations` | `visual.analysis.completed` | `BatchAnalysisResult.observations.len()` | 有效帧观察数；趋近于 0 时表示 JSON 解析全面失败 |
| `visual.analysis.errors` | `visual.analysis.partial_errors` | `BatchAnalysisResult.errors.len()` | JSON 解析失败批次数；连续 > 0 应考虑模型或 prompt 兼容性问题 |
| `visual.analysis.duration_s` | `visual.analysis.completed` | 函数级 `Instant::now()` 计时 | 端到端分析耗时；根据帧数量预估，正常 200 帧 ≈ 40-120s（取决于模型延迟） |
| `semaphore.permit_wait_ms` | `analyzer.rs` 内 tracing | `acquire_owned()` 前后的 `Instant::now()` | 并发争抢程度；wait > 5000ms 表示 max_concurrency 太小或 API 响应变慢 |

### Alert Thresholds

| Metric | Warning | Critical | Action |
|--------|---------|----------|--------|
| `template.render.elapsed_us` | > 1000μs | > 10000μs | 检查模板文件大小（> 50KB 需拆分）和 regex 模式（是否存在灾难性回溯） |
| `frame_extract.count` = 0 | — | 任何一次 | 检查 `${video_path}` 是否存在、FFmpeg 可执行文件路径、视频编码格式是否被支持 |
| 单次分析 JSON 解析失败率 | > 5% (1/20 批次) | > 15% (3/20 批次) | 检查 prompt 中 JSON 格式约束的措辞；验证模型是否真的支持 `response_format=json_object`；在 `validate_output()` 中增加更宽容的 fallback 解析器 |
| `visual.analysis.observations` = 0 | — | 任何一次 | 检查 LLM API 可用性、API key 有效性、模型是否支持图片输入；查看 `errors` 列表中的具体错误信息 |
| `semaphore.permit_wait_ms` | > 5000ms | > 30000ms | 检查 `max_concurrency` 配置值是否过小（建议 ≥ 2）；检查 API 端点响应时间是否异常；考虑增加 `timeout` 保护（D-16 模式） |
| `frame_extract.fallback` 占比 | > 30% | > 60% | 检查 FFmpeg 版本（建议 ≥ 6.0）；验证硬件加速检测（`hwaccel.rs`）是否正确识别 GPU |

### Smart Sampling Strategy

由于本系统是 Rust 库，采样策略由库发射事件 + 下游应用过滤两层组成：

| Layer | Filter | Granularity | Storage |
|-------|--------|-------------|---------|
| **库层全量捕获** | 无过滤 | `template.render` 每次调用 + `visual.analysis` 每次调用 | 结构化日志 fields (`tracing::INFO`) |
| **下游采样建议** (Phase 6 / Tauri) | `tracing::WARN+` 事件全量保留；`tracing::INFO` 事件根据日志级别配置采样 | 全量: WARN/ERROR; 按需: INFO/DEBUG | 日志文件 / 终端输出 / Tauri 事件日志 |
| **人工审核触发** | 信号驱动：当 `errors.len() > 0` 或 `observations.len() < expected * 0.5` 时，库发射 `tracing::WARN` 事件 | 仅在质量信号恶化时 | Phase 6 流水线可收集 WARN+ 事件到审核队列 |
| **基准版本对比** | 无自动化——手动运行 `cargo test --test phase4_regression` 对比 golden 输出 | 每轮开发周期（功能完成后） | git 版本化 golden 文件 |

部署到用户的桌面端后不强制采集日志——所有监控事件仅在用户启用日志（默认 stdout）时可见。生产监控的真正使用场景是 Phase 6 Documentary Pipeline 开发者调试期间启用 `RUST_LOG=info` 查看性能指标。
