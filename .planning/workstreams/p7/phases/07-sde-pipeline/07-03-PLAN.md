    导入: use std::path::Path, use crate::sde::types::{SubtitleSegment, SdeError}, use crate::sde::timestamp::parse_srt_timestamp

    包含以下公开函数：

    A. pub fn detect_encoding(data: &[u8]) -> Result<String, SdeError>
       实现编码检测链（D-08，对齐 Python ref decode_subtitle_bytes）：
       1. 尝试 UTF-8（std::str::from_utf8）
       2. 尝试 UTF-8-SIG（检查 BOM 0xEF BB BF，去除后用从_utf8）
       3. 尝试 UTF-16（检查 BOM 0xFF FE 或 0xFE FF，或用 String::from_utf16le/from_utf16be）
       4. 尝试 GBK（使用 encoding_rs 的 decode 方法）
       5. 尝试 GB2312（使用 encoding_rs）
       每个步骤成功后，检查文本中是否包含 SRT 时间戳模式（正则 `\d{2}:\d{2}:\d{2}[,.]\d{3}` 或对话内容），
       如果找到则提前返回（fast path）。全部失败则返回 SdeError::ParseSubtitle。
       返回编码名称字符串（如 "utf-8", "gbk", "utf-16-le" 等）。

    B. pub fn normalize_subtitle_text(text: &str) -> String
       对齐 Python ref normalize_subtitle_text：
       - 统一换行符为 \n（替换 \r\n → \n，\r → \n）
       - 移除 BOM（\u{feff}）
       - 移除 NUL 字节（\x00）
       - 标准化毫秒分隔符：点号→逗号（"00:00:01.000" → "00:00:01,000"）
       - 去除首尾空白

    C. pub fn parse_subtitle_file(path: &Path) -> Result<(Vec<SubtitleSegment>, String, String), SdeError>
       高级函数：读取文件→检测编码→解码→标准化→解析段落。
       1. 读取文件字节：std::fs::read(path)?
       2. 调用 detect_encoding 获取编码名
       3. 用检测到的编码解码字节为字符串
          - UTF-8/UTF-8-SIG: String::from_utf8(data)?
          - UTF-16-LE: String::from_utf16le(data) 
          - GBK/GB2312: encoding_rs::GBK.decode(&data).0.to_string()
       4. 调用 normalize_subtitle_text
       5. 解析 SRT/ASS 格式提取 SubtitleSegment 列表：
          - SRT 格式模式：序号\n时间戳\n文本\n空行
          - 使用正则或逐行解析提取 (start_time, end_time, text) 三元组
          - 时间戳格式："HH:MM:SS,mmm --> HH:MM:SS,mmm"
          - 使用 parse_srt_timestamp 将字符串转为秒数
          - ASS 格式也支持（解析 [Events] 部分的 Dialogue 行提取 Start/End/Text）
       6. 返回 (Vec<SubtitleSegment>, String 标准化文本, String 编码名)
       7. 解析失败返回 SdeError::ParseSubtitle

       注意：detect_encoding 是 CPU 密集型——在 pipeline.rs 中调用此函数时应当通过 tokio::task::spawn_blocking 包装（详见 07-04-PLAN.md 的 pipeline.rs）。本模块只实现同步函数。

    D. 私有辅助函数：
       - fn parse_srt_blocks(text: &str) -> Vec<SubtitleSegment>
       - fn parse_ass_dialogues(text: &str) -> Vec<SubtitleSegment>
       - fn extract_text_from_srt(text: &str) -> String（移除时间戳和序号行，只保留对话文本）
       - fn extract_text_from_ass(text: &str) -> String
       - fn has_srt_timecodes(text: &str) -> bool（用于 fast path 判断）

       6 步回退策略，对齐 Python ref generate_short_summary.py parse_and_fix_json：
       1. 直接解析：serde_json::from_str::<Value>(text) 成功 → 返回原文本
       2. 代码块提取：去掉 ```json / ``` 标记后重试
       3. 首对象提取：找到第一个 { 或 [ 到匹配的 } 或 ]
       4. 双大括号修复：{{...}} → {...}
       5. 尾逗号移除：",}" → "}" 和 ",]" → "]"
       6. 单引号转双引号：仅当文本不包含双引号时
       全部失败 → 返回原始字符串（调用方 parse_script 负责清晰报错）

    D. pub fn parse_script(
        raw_json: &str,
        task_dir: &Path,
    ) -> Result<crate::script::types::Script, SdeError>
       将修复后的 JSON 解析为 Script（D-22, D-24, D-26）。
       1. 调用 repair_json(raw_json)
       2. serde_json::from_str::<Value>(repaired) → Err → SdeError::JsonRepair
       3. 获取数组：value.as_array() OR value["items"].as_array() OR value["clips"].as_array()（D-22）
       4. 无有效数组 → SdeError::JsonRepair
       5. 逐项反序列化：serde_json::from_value::<ScriptClip>(item)

          - 反序列化失败 → log warning + 跳过该项（不中断整个解析）
       6. clips 为空 → SdeError::ScriptGeneration（G5 Empty Script Guard）
       7. 调用 crate::script::validate(&clips)（D-24）→ 失败 → SdeError::Validation
       8. 保存最终脚本：tokio::fs::write(task_dir.join("script_final.json"), &serde_json::to_string_pretty(&clips)?).await?（D-17）
       9. Ok(clips)

<threat_model>
## Assets
- **Subtitle content** (输入文件，用户本地文件)
- **LLM API responses** (可能包含敏感内容)
- **Generated scripts** (中间产物，保存在 task_dir)
- **API keys** (SDE 不直接持有，通过 LlmProvider trait 间接使用)

## Entry Points
- parse_subtitle_file() — 用户提供的字幕文件路径
- repair_json() — LLM 输出的 JSON 字符串
- step_analyze_plot() / step_generate_script() — LLM API 调用

## Trust Boundaries
| Boundary | Description |
|----------|-------------|
| subtitle file → parse_subtitle_file | 外部文件内容（可能是恶意构造的 SRT 文件） |
| LLM API → repair_json | 不受信任的网络响应（格式可能错误，内容不可控） |

## STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-7-06 | Denial of Service | subtitle.rs parse_subtitle_file | mitigate | 编码检测链在 detect_encoding 内严格限制尝试次数（最多 5 种编码）。超大文件由 std::fs::read 自动处理（Rust 分配机制会抛出 OOM 而非逻辑错误）。regex 匹配使用固定长度模式。 |
| T-7-07 | Tampering | script_gen.rs repair_json | mitigate | repair_json 是纯内存操作（无副作用）。parse_script 使用 serde_json 的严格解析（类型检查、值范围检查）。无效内容安全跳过（log warning + 跳过该片段），不 panic。 |
| T-7-08 | Information Disclosure | step_analyze_plot / step_generate_script | mitigate | LLM 错误消息不包含 API key（通过 LLMError 抽象层传递，SdeError::PlotAnalysis/ScriptGeneration 只封装用户可读的 details 字符串）。LLMError 的具体内容在管道路径上丢失。 |
| T-7-09 | Spoofing | LlmProvider::generate_text 调用 | accept | SDE 不验证 LLM provider 的身份——这是 Phase 2 的责任（registry 中 provider 由 register_all_providers() 注册）。SDE 只通过 trait 方法调用。风险低：provider 配置在用户本地的 config.toml 中。 |
</threat_model>
