## 1. System Classification

**System Type:** Content Generation Pipeline

**Description:**
SDE Pipeline 是一个内容生成流水线，从字幕文件（SRT/ASS）解析中文短剧对话，通过两步 LLM 文本生成（剧情提炼 → 解说脚本生成）产生带 OST 标记的 JSON 脚本。输出脚本被下游视频处理流水线消费，用于自动剪辑配音生成解说视频。系统运行在 Rust 库（`src/sde/`）内，通过项目已有的 `src/llm/` 抽象层调用 OpenAI 兼容 API。

**Critical Failure Modes:**
1. LLM 输出 JSON 格式错误导致脚本解析失败，流水线中断
2. OST=1（原声）标记的时间戳与原始字幕不匹配，导致剪辑点错误
3. 解说脚本生成质量低（不符合短剧解说风格），视频缺少吸引力
4. 字幕编码探测失败（GBK/UTF-16），无法正确读取中文字幕文件
5. LLM API 调用超时或返回空响应，流水线无中间产物可恢复

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** AI-assisted short drama (短剧) video narration and automated editing — a sub-sector of Chinese short-form video content creation (短视频/微短剧行业)

**User Population:** Individual video content creators and small studios producing short drama commentary/narration videos for Chinese platforms (Douyin/TikTok China, Kuaishou, Bilibili). These creators are typically experienced in short video production but seek to scale output through automation.

**Stakes Level:** Medium
The output is creative content rather than safety-critical material. However, poor narration quality means the final video is unpublishable on competitive platforms, and the full video processing pipeline (TTS --> clipping --> merging --> compositing) represents significant compute time and system resources. Non-compliance with AI content labeling regulations carries platform-level risk (content takedown, account penalties).

**Output Consequence:** The JSON script directly drives fully automated video assembly. A flawed script produces a flawed video -- the creator must re-run the entire pipeline, wasting time and compute. The produced video is published on content platforms where viewer retention, engagement, and algorithmic recommendation depend entirely on narration quality.

### Known Failure Modes in This Domain

1. **AI 味过重（Template Voice Syndrome）**
   解说文案使用千篇一律的模板化语言，缺乏个性吐槽、上帝视角分析和角色心理描述。观众能在几秒内识别出"这是 AI 写的"，导致跳出率飙升。根本原因：LLM 偏好输出安全、中性的书面语，需要明确的风格约束和示例引导才能产出口语化、有态度的解说。

2. **OST 分配失当（Wrong Emotional Emphasis）**
   LLM 将原声分配给平淡对话而错过关键情感爆发点（愤怒、崩溃、逆袭瞬间），或者 OST=0 的解说片段覆盖了本该保留的原声台词。根本原因：LLM 对"情感强度"的感知与人类不一致，需要更明确的"关键情绪点"分类指引。

3. **时间戳交叉或断裂（Timestamp Misalignment）**
   生成的脚本片段时间戳互相重叠（导致剪辑时重复画面）或出现间隙（导致黑屏/跳帧），违反"时间戳绝对不能重叠"的核心约束。根本原因：LLM 在处理时间区间边界时缺乏精确计算能力，尤其是从密集字幕分段时易出错。

4. **因果逻辑断裂（Causal Discontinuity）**
   在压缩到 1/3 时长的过程中，LLM 删除了关键因果链环节，导致观众看到结果却不理解原因。例如跳过"主角发现阴谋"直接跳到"主角反击"，中间的关键推理过程缺失。根本原因：LLM 在"摘要"模式下倾向于保留结果而非过程，而短剧解说需要保留因果链条。

## 2. Framework Decision

**Selected Framework:** Project-native AI infrastructure (`src/llm/` + `src/prompt/` + `async-openai` 0.36)

**Version:** async-openai 0.36 (already in Cargo.toml)

**Rationale:**
All mainstream AI/LLM frameworks (LangChain, CrewAI, LangGraph, LlamaIndex, OpenAI Agents SDK, etc.) are Python/TypeScript exclusive -- none support Rust. Phase 7 SDE requires only two text LLM calls (plot analysis --> script generation) + JSON repair, a pattern already validated in `src/documentary/script_gen.rs`. The project's `src/llm/LlmProvider::generate_text()` (with `LlmResponseFormat::Json`) and `src/prompt/PromptManager::render_prompt()` fully cover this need. Introducing any external framework would add unnecessary abstraction overhead and crate dependencies with zero benefit.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| rustic-ai/rig (Rust-native LLM framework) | Project's own LlmProvider trait already provides equivalent abstraction; adding rig would be an extra dependency for duplicated functionality. May be reconsidered if future phases need cross-module shared patterns or formal tool-use abstractions. |
| LangChain (Python) | Python-only -- incompatible with Rust rewrite |
| CrewAI (Python) | Python-only -- incompatible with Rust rewrite |
| OpenAI Agents SDK (Python/TS) | No Rust support; project already uses async-openai directly |
| Claude Agent SDK (Python/TS) | No Rust support; project uses model-agnostic OpenAI-compatible protocol |

**Vendor Lock-In Accepted:** No -- model-agnostic via OpenAI-compatible protocol; `async-openai` supports any `/v1/chat/completions` endpoint

### Entry Point Pattern: Two-Step Text LLM with Prompt Templates

```rust
use std::collections::HashMap;
use std::sync::Arc;
use crate::llm::provider::LlmProvider;
use crate::llm::types::LlmResponseFormat;
use crate::prompt::manager::PromptManager;

/// 两步 LLM 文本生成 -- SDE 核心模式
///   Step 1: PromptManager::render_prompt() + LlmProvider::generate_text() -- 剧情分析
///   Step 2: PromptManager::render_prompt() + LlmProvider::generate_text() -- 脚本生成 (JSON)
async fn generate_sde_script(
    provider: Arc<dyn LlmProvider>,      // text model provider from Registry
    prompt_manager: &PromptManager,      // renders prompt templates with variables
    subtitle_text: &str,                 // parsed, normalized subtitle content
) -> Result<String, LLMError> {
    // ===== Step 1: Plot Analysis (text output) =====
    let plot_prompt = prompt_manager.render_prompt(
        "short_drama_narration",   // category
        "plot_analysis",           // name
        Some("v1.0"),              // version (or None for default)
        &HashMap::from([
            ("subtitle_content", subtitle_text),
            ("language", "zh-CN"),
        ]),
    )?;  // PromptManager releases RwLock before returning

    let plot_analysis = provider
        .generate_text(
            &plot_prompt,
            Some("你是一个专业的短剧剧情分析师。提取人物关系、冲突转折、剧情高潮。"), // system
            Some(1.0),     // temperature
            Some(4096),    // max_tokens -- always explicit
            None,          // response_format -- Text output
        )
        .await?;

    // ===== Step 2: Script Generation (JSON output) =====
    let script_prompt = prompt_manager.render_prompt(
        "short_drama_narration",
        "script_generation",
        Some("v1.0"),
        &HashMap::from([
            ("plot_analysis", &plot_analysis),  // inject Step 1 output
            ("language", "zh-CN"),
            ("style", "幽默风趣"),
        ]),
    )?;

    let script_json = provider
        .generate_text(
            &script_prompt,
            Some("你是一个短剧解说脚本生成专家。严格按 JSON 格式输出。"),
            Some(1.0),
            Some(8192),                          // more tokens for JSON array output
            Some(LlmResponseFormat::Json),       // triggers json_object + fallback
        )
        .await?;

    Ok(script_json)
}
```

### Specific Pitfalls (5)

1. **`LlmProvider::generate_text` 签名是 `&self` -- Provider 实例通过 `Arc` 共享** -- `OpenAiCompatibleProvider` 内部 `client: Client<OpenAIConfig>` 是 `Clone` 的（async-openai 的 Client 内部是 Arc），所以多个 `generate_text` 调用可以安全并发。SDE 代码不需要 `Arc::clone` provider 或使用 `Mutex`。正确的获取方式：`let provider = registry.get("openai_text")?;` 得到 `Arc<dyn LlmProvider>`，调用时 `provider.generate_text(...)` 自动解引用。

2. **`PromptManager` 内部的 `std::sync::RwLock` 不能在 `.await` 期间持有** -- `PromptManager.render_prompt()` 内部获取 `registry.read().unwrap()` 返回 `RwLockReadGuard`。如果 render 返回前持有这个 guard 跨越 `.await` 点，会阻塞 tokio worker 线程。**解决方案**：`render_prompt()` 自行管理锁生命周期 -- 它在函数返回前已释放 guard（返回的是 `String`）。SDE 代码只需要确保不写这样的模式：`let guard = prompt_manager.registry.read().unwrap(); let result = some_async_fn().await;` -- 直接调用 `render_prompt()` 是安全的。

3. **`LlmResponseFormat::Json` 不保证输出是合法 JSON -- 必须叠加 `repair_json()`** -- `openai_compatible.rs` 的 `generate_text_with_json_fallback()` 处理了 `response_format=json_object` 的网关兼容性问题，但并不修改 LLM 的响应内容。LLM 仍可能输出：格式正确但空数组、字段名不匹配（`"OST"` vs `"ost"`）、值类型错误（`"OST": "0"` 字符串而非数字）。SDE 的 `repair_json()` + `parse_script_clips()` 必须作为第二道防线。模式参考 `src/documentary/script_gen.rs` 的 `strip_and_repair_json()` + `parse_script_clips()`。

4. **`CreateChatCompletionRequestArgs` 不是 `Clone`** -- async-openai 0.36 的 builder pattern `CreateChatCompletionRequestArgs` 没有实现 `Clone`。在 `openai_compatible.rs` 的 JSON 回退路径中已经正确处理（用 `build_text_messages()` 重建请求）。**SDE 代码不需要直接操作 `CreateChatCompletionRequestArgs` -- 所有 LLM 调用都应通过 `LlmProvider` trait。** 如果未来需要直接使用 async-openai 的 stream API，注意 builder 一次 build 后不能复用。

5. **`tokio::task::spawn_blocking` 用在 subtitle 编码探测中** -- 字幕编码探测（尝试 utf-8，回退 utf-16，回退 gbk，回退 gb2312）是 CPU 密集型操作，需要在 `subtitle.rs` 中用 `tokio::task::spawn_blocking(move || decode_bytes(&raw_bytes))` 包装，避免阻塞 tokio 的 async worker 线程。纪录片 `openai_compatible.rs` 的 `analyze_images` 中已有先例（`spawn_blocking` 处理图片预处理）。这是 SDE 特有的 pitfall -- 纪录片不涉及文件编码探测。

/// JSON 修复：6 步回退策略（对齐 Python 版 parse_and_fix_json）
///
/// 处理 LLM 常见的输出格式问题，按优先级尝试以下修复策略：
/// 1. 直接解析 (serde_json::from_str)
/// 2. 剥离 markdown 代码块 (```json ... ```)
/// 3. 提取第一个完整 JSON 对象（从第一个 { 到匹配的 }）
/// 4. 双大括号修复 ({{...}} → {...})
/// 5. 尾逗号移除 (replace ",}"→"}" and ",]"=>"]")
/// 6. 单引号转双引号 (仅在无双引号时)
pub fn repair_json(raw: &str) -> String {
    let text = raw.trim();

    // Strategy 1: Direct parse
    if serde_json::from_str::<serde_json::Value>(text).is_ok() {
        return text.to_string();
    }

    // Strategy 2: Strip code fence
    let text = text
        .trim_start_matches("```json")
        .trim_start_matches("```")
        .trim_end_matches("```")
        .trim();
    if serde_json::from_str::<serde_json::Value>(text).is_ok() {
        return text.to_string();
    }

    // Strategy 3: Extract first JSON object
    if let Some(obj) = extract_first_json_object(text) {
        if serde_json::from_str::<serde_json::Value>(&obj).is_ok() {
            return obj;
        }
    }

    // Strategy 4: Strip doubled braces {{...}} → {...}
    if text.starts_with("{{") && text.ends_with("}}") && text.len() > 4 {
        let stripped = &text[1..text.len() - 1];
        if serde_json::from_str::<serde_json::Value>(stripped).is_ok() {
            return stripped.to_string();
        }
    }

    // Strategy 5: Remove trailing commas in objects and arrays
    let repaired = text.replace(",}", "}").replace(",]", "]");
    if serde_json::from_str::<serde_json::Value>(&repaired).is_ok() {
        return repaired;
    }

    // Strategy 6: Convert single quotes to double quotes (only when no double quotes)
    if !text.contains('"') && text.contains('\'') {
        let repaired = text.replace('\'', "\"");
        if serde_json::from_str::<serde_json::Value>(&repaired).is_ok() {
            return repaired;
        }
    }

    // Fallback: return as-is (parse_script will produce a clear error)
    text.to_string()
}

/// 从文本中提取第一个完整 JSON 对象/数组
fn extract_first_json_object(text: &str) -> Option<String> {
    let chars: Vec<char> = text.chars().collect();
    let start = chars.iter().position(|&c| c == '{' || c == '[')?;
    let open = chars[start];
    let close = if open == '{' { '}' } else { ']' };

    let mut depth = 0i32;
    let mut in_string = false;
    let mut escape = false;

    for i in start..chars.len() {
        let c = chars[i];
        if escape { escape = false; continue; }
        if c == '\\' && in_string { escape = true; continue; }
        if c == '"' { in_string = !in_string; continue; }
        if !in_string {
            if c == open { depth += 1; }
            else if c == close {
                depth -= 1;
                if depth == 0 {
                    return Some(chars[start..=i].iter().collect());
                }
            }
        }
    }
    None
}

/// 将 LLM 输出的 JSON 解析为 Script（带单片段跳过和日志）
pub fn parse_script(raw_json: &str) -> Result<crate::script::types::Script, SdeError> {
    let repaired = repair_json(raw_json);

    // Parse as untyped Value first
    let value: serde_json::Value = serde_json::from_str(&repaired)
        .map_err(|e| SdeError::JsonRepair {
            details: format!("JSON 解析失败 (repair后): {}", e),
        })?;

    // Accept top-level array or { "items": [...] } or { "clips": [...] }
    let items = value
        .as_array()
        .map(|a| a.clone())
        .or_else(|| value.get("items").and_then(|v| v.as_array().map(|a| a.clone())))
        .or_else(|| value.get("clips").and_then(|v| v.as_array().map(|a| a.clone())))
        .ok_or_else(|| SdeError::JsonRepair {
            details: "JSON 顶层不是数组且无 items/clips 字段".to_string(),
        })?;

    // Deserialize each item individually, skipping invalid ones
    let mut clips = crate::script::types::Script::with_capacity(items.len());
    for (i, item) in items.into_iter().enumerate() {
        let mut obj = item;
        // Default OST to 0 (NarrationOnly) if missing -- SDE uses only OST=0/1 (D-26)
        if obj.get("OST").is_none() && obj.get("ost").is_none() {
            obj["OST"] = serde_json::Value::Number(serde_json::Number::from(0));
        }

        match serde_json::from_value::<crate::script::types::ScriptClip>(obj) {
            Ok(clip) => clips.push(clip),
            Err(e) => {
                tracing::warn!("SDE: 跳过无效脚本片段 #{}: {}", i + 1, e);
            }
        }
    }

    if clips.is_empty() {
        return Err(SdeError::ScriptGeneration {
            details: "未解析到任何有效脚本片段".to_string(),
        });
    }

    // Validate using Phase 5 validators (D-24)
    crate::script::validate_script(&clips)?;

    Ok(clips)
}
```

/// Subtitle truncation for plot analysis -- preserve head and tail
fn truncate_subtitle(text: &str, max_chars: usize) -> String {
    if text.chars().count() <= max_chars {
        return text.to_string();
    }
    let head = text.chars().take(max_chars / 3 * 2).collect::<String>();
    let tail = text.chars().rev().take(max_chars / 3).collect::<String>()
        .chars().rev().collect();
    format!("{}\n\n...（中间省略 {} 字）...\n\n{}",
        head, text.chars().count() - head.len() - tail.len(), tail)
}
```

### 4b.1 Structured Outputs with Serde (Rust equivalent of Pydantic)

/// Custom _id deserializer: accepts integer AND float (e.g., LLM outputs 1.0)
fn deserialize_id<'de, D: de::Deserializer<'de>>(d: D) -> Result<i64, D::Error> {
    let val = serde_json::Value::deserialize(d)?;
    match val {
        serde_json::Value::Number(n) => {
            if let Some(i) = n.as_i64() { Ok(i) }
            else if let Some(f) = n.as_f64() {
                let i = f as i64;
                if i as f64 != f || i == i64::MAX || i == i64::MIN {
                    Err(de::Error::custom("_id 数值超出有效范围"))
                } else { Ok(i) }
            } else {
                Err(de::Error::custom("_id 必须是数字"))
            }
        }
        _ => Err(de::Error::custom("_id 必须是数字")),
    }
}

**Step 3: Retry logic (layered):**

```
Layer 1 (HTTP transport): OpenAiCompatibleProvider configures ExponentialBackoff
  max_elapsed_time = max_retries * 10 seconds
  Retries on: network errors, 5xx, rate limits
  Does NOT retry on: 400 (bad request), 401 (auth), 422 (validation)

Layer 2 (JSON repair): 6-strategy repair_json() in memory
  Zero additional API calls
  Falls back through: direct parse → code fence → first object → double braces → trailing comma → single quotes

Layer 3 (fail-fast): step_generate_script returns immediately on LLMError
  No re-prompting with "please fix your JSON"
  Rationale: same prompt producing valid JSON again is unlikely; save the failure for debugging

Layer 4 (validation): validate_script catches semantic errors
  Empty clips → SdeError::Validation
  Overlapping timestamps → SdeError::Validation
  Caller (webui) can retry with different temperature or manual edits
```

### 4b.2 Async-First Design

**How async works in this framework:**

The project uses `tokio` as the async runtime + `async-trait` for `LlmProvider` trait methods.

```rust
// All SDE step functions are async, running on the tokio runtime
async fn step_analyze_plot(state: &mut SdePipelineState, ...) -> Result<(), SdeError>;
async fn step_generate_script(state: &mut SdePipelineState, ...) -> Result<(), SdeError>;

// Main orchestrator -- sequential await
pub async fn run_sde(
    request: SdeRequest,
    config: &AppConfig,
    proxy: Option<&ProxySection>,
    registry: &Registry,
    prompt_manager: &PromptManager,
) -> Result<PathBuf, SdeError>;
```

**The one common mistake: holding `std::sync::RwLock` guard across `.await`**

```rust
// WRONG -- this blocks the tokio worker thread during .await
let guard = prompt_manager.inner.lock().unwrap();   // hypothetical
let prompt = guard.get_prompt(...);
provider.generate_text(&prompt, ...).await;          // BUG: RwLockReadGuard held across await

// CORRECT -- PromptManager::render_prompt() releases the lock before returning
let prompt = prompt_manager.render_prompt(...)?;     // RwLock released inside render_prompt
provider.generate_text(&prompt, ...).await;          // OK: no lock held
```

The `PromptManager` in this project uses `std::sync::RwLock` (not `tokio::sync::RwLock`). Holding a `std::sync::RwLockReadGuard` across an `.await` point does not cause a runtime panic (as `tokio::Mutex` would), but it **blocks the entire tokio worker thread** during the `.await`, preventing all other tasks on that thread from making progress. The `render_prompt()` method correctly avoids this -- it acquires, reads, renders, and releases inside one synchronous call.

**SDE-specific concern**: `subtitle.rs` encoding detection (utf-8 → utf-16 → gbk → gb2312) is CPU-intensive. Wrap it in `tokio::task::spawn_blocking`:

```rust
async fn parse_subtitle_file(path: &Path) -> Result<(Vec<SubtitleSegment>, String), SdeError> {
    let raw_bytes = tokio::fs::read(path).await?;
    let path_clone = path.to_path_buf();

    // CPU-bound encoding detection -- must not block async runtime
    let (segments, text) = tokio::task::spawn_blocking(move || {
        detect_encoding_and_parse(&raw_bytes, &path_clone)
    })
    .await
    .map_err(|e| SdeError::ParseSubtitle {
        details: format!("解码任务失败: {}", e),
    })??;

    Ok((segments, text))
}
```

**Stream vs. Await:**

SDE uses `generate_text()` (non-streaming) for both LLM calls:

- `generate_text()` returns `Result<String, LLMError>` -- complete response arrives before method returns. Required for `repair_json()` + `serde_json::from_str()` parse pipeline.
- `generate_text_stream()` returns `Stream<Item = Result<String, LLMError>>` -- token-by-token. Useful for UI progress display (streaming the JSON as it arrives). **Do NOT use in SDE step functions** -- JSON parsing requires the complete string, and incremental parsing adds complexity with no benefit.

If future phases need UI progress for SDE, the correct pattern is:
1. Use `generate_text()` in the pipeline
2. Write intermediate artifacts to `task_dir`
3. webui polls for artifact existence to show progress
4. No streaming in the pipeline itself

### 4b.3 Prompt Engineering Discipline

**System vs. User Prompt Separation:**

Every LLM call uses explicit `system_prompt` + `user prompt` (template-rendered) separation:

```rust
// Step 1 (Plot Analysis):
// System: "你是一个专业的短剧剧情分析师。提取人物关系、冲突转折、剧情高潮。"
// User:   rendered template with ${subtitle_content}, ${language}

// Step 2 (Script Generation):
// System: "你是一个短剧解说脚本生成专家。严格按 JSON 格式输出 ScriptClip 数组。每个片段包含 _id, timestamp, picture, narration, OST 字段。"
// User:   rendered template with ${plot_analysis}, ${language}, ${style}
```

**Few-shot examples:**

Prompt templates embed static few-shot examples (no runtime retrieval). For SDE `script_generation` v2.0, the template content should include:

```
## 输出格式要求
严格按以下 JSON 格式返回，包含 items 数组：

```json
{
  "items": [
    {
      "_id": 1,
      "timestamp": "00:00:01,200-00:00:08,500",
      "picture": "女主角在办公室门口听到同事议论，表情从困惑变为震惊",
      "narration": "播放原片+3",
      "OST": 1
    },
    {
      "_id": 2,
      "timestamp": "00:00:08,500-00:00:15,200",
      "picture": "女主角深吸一口气推开办公室门",
      "narration": "女主角万万没想到，上班第一天就听到了关于自己的惊天大瓜。",
      "OST": 0
    }
  ]
}
```

Key conventions that must be in the prompt template:
- OST=1 fragments have `narration` field set to `"播放原片+N"` (where N = segment length in seconds). The pipeline detects this prefix to skip TTS (D-23).
- OST=0 fragments have full narration text.
- Timestamps must densely cover the full video timeline without gaps or overlaps.
- OST=1 fragments should be 3-8 seconds each, distributed across the video (not all at start or end).

**`max_tokens` must be set explicitly -- never leave unbounded:**

```rust
// WRONG (unbounded -- consumes context window and budget)
provider.generate_text(&prompt, Some(sys), Some(temp), None, ...).await?;

// CORRECT (explicit upper bound for each step)
const PLOT_ANALYSIS_MAX_TOKENS: u32 = 4096;
const SCRIPT_GENERATION_MAX_TOKENS: u32 = 8192;

provider.generate_text(&prompt, Some(sys), Some(temp), Some(PLOT_ANALYSIS_MAX_TOKENS), None).await?;
provider.generate_text(&prompt, Some(sys2), Some(temp), Some(SCRIPT_GENERATION_MAX_TOKENS), Some(LlmResponseFormat::Json)).await?;
```

Rationale: Chinese text is approximately 1:1 char-to-token ratio. A 10-minute short drama subtitle (~2000 chars) generates ~2000 input tokens. The script JSON output can be 4000-8000 tokens for 15-25 clips. Setting `max_tokens = 8192` gives enough headroom without allowing degenerate long outputs.

### 4b.4 Context Window Management

SDE's context management focuses on subtitle input length control and script output boundary enforcement.

**Subtitle Truncation (Input to Plot Analysis):**

```rust
/// Truncate Chinese subtitle text preserving head and tail
fn truncate_subtitle(text: &str, max_chars: usize) -> String {
    if text.chars().count() <= max_chars {
        return text.to_string();
    }
    let head_len = max_chars / 3 * 2;
    let tail_len = max_chars - head_len;
    let head: String = text.chars().take(head_len).collect();
    let tail: String = text.chars().rev().take(tail_len).collect::<String>()
        .chars().rev().collect();
    format!("{}\n\n...（中间省略 {} 字）...\n\n{}",
        head, text.chars().count() - head_len - tail_len, tail)
}
```

Default `max_chars = 6000` (approximately 6000 Chinese tokens = fits easily in 16K context window with prompt + output overhead). For episodes with subtitles > 6000 characters, the middle portion is sacrificed -- this is acceptable because critical plot points are usually concentrated in the opening and closing of an episode.

**OST=1 Precise Timestamp Mapping (Output Validation):**

LLM output timestamps are often imprecise. SDE maps them against original subtitle segments:

```rust
// src/sde/timestamp.rs
#[derive(Debug, Clone)]
pub struct SubtitleSegment {
    pub index: usize,
    pub start_secs: f64,
    pub end_secs: f64,
    pub text: String,
}

/// Match LLM output timestamp range to nearest original subtitle segments
/// Used for OST=1 clipping precision (D-29)
pub fn find_precise_range(
    llm_timestamp: &str,           // "00:00:05,000-00:00:15,000"
    segments: &[SubtitleSegment],
) -> Option<(f64, f64)> {
    let parts: Vec<&str> = llm_timestamp.splitn(2, '-').collect();
    if parts.len() != 2 { return None; }

    let llm_start = parse_time_to_secs(parts[0]).ok()?;
    let llm_end = parse_time_to_secs(parts[1]).ok()?;

    // Find segments that overlap with the LLM range (with 1s tolerance)
    let matched: Vec<&SubtitleSegment> = segments.iter()
        .filter(|s| s.start_secs >= llm_start - 1.0 && s.end_secs <= llm_end + 1.0)
        .collect();

    if matched.is_empty() { return None; }

    Some((matched.first()?.start_secs, matched.last()?.end_secs))
}
```

**Post-processing compaction:** If total script duration > video duration (LLM overestimates), the pipeline rejects with a clear error -- no automatic compaction. This is intentional (Phase 6 fail-fast design): silent compaction would produce a faulty video.

**Caching strategy:**

SDE input (subtitle files) is nearly unique per episode -- exact-match caching has low hit rate. However, for webui retries with the same file:

```rust
/// Content-addressed cache for plot analysis results
async fn with_plot_cache(
    content: &str,
    provider: &dyn LlmProvider,
    prompt_manager: &PromptManager,
    temperature: f64,
    task_dir: &Path,
) -> Result<String, SdeError> {
    use sha2::{Sha256, Digest};

    let hash = Sha256::digest(content.as_bytes());
    let cache_key = format!("plot_analysis_{:x}", hash);
    let cache_path = task_dir.join(&cache_key);

    // Check disk cache
    if cache_path.exists() {
        return Ok(tokio::fs::read_to_string(&cache_path).await
            .map_err(|e| SdeError::Io { source: e })?);
    }

    // LLM call
    let result = step_analyze_plot(content, provider, prompt_manager, temperature).await?;

    // Write cache
    tokio::fs::write(&cache_path, &result).await
        .map_err(|e| SdeError::Io { source: e })?;

    Ok(result)
}
```

No semantic cache needed -- subtitle text is deterministic and exact-match cache is sufficient for retry scenarios.

## 5. Evaluation Strategy

### 5.1 Dimension Overview

All 7 evaluation dimensions are grounded in the domain rubric ingredients documented in Section 1b. The 5 domain-expert dimensions (黄金开场, 爽点放大, OST分配合理性, 叙事连贯性, 语言风格) are taken directly from Section 1b's "What Domain Experts Evaluate Against" with concrete Good/Bad criteria preserved in domain language. Two structural dimensions (JSON Schema Compliance, Timestamp Validity) are added to cover critical failure modes 1 and 3 from Section 1.

| # | Dimension | Domain Source | Priority | Measurement |
|---|-----------|---------------|----------|-------------|
| E1 | JSON Schema Compliance | Section 1 Failure Mode 1 | Critical | Code (Rust integration test) |
| E2 | Timestamp Validity | Section 1 Failure Mode 3 | Critical | Code (Rust integration test) |
| E3 | 黄金开场 (Opening Hook) | Section 1b expert dimension 1 | High | LLM Judge |
| E4 | 爽点放大 (Highlighting Exciting Moments) | Section 1b expert dimension 2 | High | LLM Judge |
| E5 | OST分配合理性 (OST Allocation) | Section 1b expert dimension 3 | High | Code + LLM Judge |
| E6 | 叙事连贯性 (Narrative Coherence) | Section 1b expert dimension 4 | High | LLM Judge |
| E7 | 语言风格 (Narration Voice) | Section 1b expert dimension 5 | Medium | LLM Judge |

### 5.2 Rubric Definitions

Each rubric is defined in domain-specific language from Section 1b, not generic evaluation terminology.

---

#### E1: JSON Schema Compliance (Critical -- Code)

**PASS:** `repair_json()` + `parse_script()` succeeds on first attempt (Strategy 1 direct parse). All required fields present with correct types: `_id` as integer, `timestamp` as `"HH:MM:SS,mmm-HH:MM:SS,mmm"`, `picture` as non-empty string, `narration` as non-empty string, `OST` as integer 0 or 1. Array contains at least 5 valid `ScriptClip` items. No items skipped during per-item parsing.

**FAIL:** `repair_json()` exhausts all 6 strategies and returns invalid JSON. `serde_json::from_str` returns error. All items are skipped during per-item parsing (empty clips array). Field type mismatches (string OST, float `_id` outside acceptable range, missing `timestamp`). Validation error from `validate_script()`.

**Measurement:** Code -- Rust `#[tokio::test]` integration test calls `generate_sde_script()` with mock provider, feeds known-good and known-bad JSON responses, asserts parse outcome.

**Rationale:** Section 1 Failure Mode 1 -- JSON failure interrupts the entire pipeline. This is the highest-impact structural check because a bad parse wastes all downstream video processing (TTS -> FFmpeg clipping -> merge -> concat -> composite), which can take 10-30 minutes of compute time.

---

#### E2: Timestamp Validity (Critical -- Code)

**PASS:** Every `ScriptClip.timestamp` conforms to `"HH:MM:SS,mmm-HH:MM:SS,mmm"` regex. No two segments have overlapping timestamp ranges. Timeline is densely covered (no gaps > 2 seconds between consecutive segments). First segment starts at or near 00:00:00,000. Last segment end matches approximate video duration. Total script duration <= video duration.

**FAIL:** Overlapping timestamps (e.g., segment 3 ends at 00:05:30,000 but segment 4 starts at 00:05:25,000). Gaps between segments (e.g., segment 3 ends at 00:03:00,000 and segment 4 starts at 00:05:00,000). Timestamp format invalid (e.g., `"00:00:05,000 - 00:00:15,000"` with spaces, or `"00:00:05.000-00:00:15.000"` with dots). Total script duration exceeds video duration.

**Measurement:** Code -- Rust `validate_script()` function (Phase 5, reused per D-24) + SDE-specific timestamp overlap check in `pipeline.rs`. Integration test asserts that known-overlapping input is rejected.

**Rationale:** Section 1 Failure Mode 3 -- timestamp misalignment causes corrupted video output (overlapping frames or black screen gaps). The LLM commonly makes off-by-one errors on timestamp boundaries; this is the guard that catches them.

---

#### E3: 黄金开场 (Opening Hook) (High -- LLM Judge)

**PASS:** The first 3 seconds of narration directly presents the core conflict, a suspense hook, or a defining character trait. Uses recognized opening techniques from the domain (Section 1b): "身为一个...", "而这一天...", "没想到...", "你绝对想不到...", or equivalent rhetorical hooks. The hook is plot-relevant (not generic filler). A viewer unfamiliar with the drama immediately understands "why this story is worth watching."

**FAIL:** Flat exposition that describes background/setting without tension (e.g., "这个故事发生在..."). No hook technique used. Generic opening that could apply to any short drama (no specificity). First segment is OST=1 (original sound) without setup context, leaving the viewer confused. Opening does not serve the "3-second rule" for platform retention.

**Measurement:** LLM Judge -- Python/script calls OpenAI-compatible API with instruction: "你是短剧解说质量评估专家。评价以下解说脚本的开场是否符合'黄金开场'标准：前3秒是否抛出冲突/悬念/角色定性。输出 PASS/FAIL 及理由。" Requires calibration against 3 human-scored examples before trusting.

**Calibration:** Run 10 known-good and known-bad openings past the LLM judge. Adjust prompt until agreement with human evaluator >= 80%. Re-calibrate every 2 weeks or after any prompt template change.

---

#### E4: 爽点放大 (Highlighting Exciting Moments) (High -- LLM Judge)

**PASS:** Script identifies 3-5 key climax moments (protagonist reversal, antagonist defeat, emotional outburst, intelligence play, plot twist) and amplifies each with energetic phrasing, intensified rhythm, or explicit emotional commentary. The narration pace visibly accelerates around climax segments (shorter sentences, stronger language). Key plot peaks have OST=1 (original sound) preserved for maximum emotional impact. Reader can identify "this is the exciting part" without watching the original drama.

**FAIL:** Flat sequential retelling where all segments have uniform emotional weight. No distinction between setup, climax, and resolution. Key climax moments are glossed over in a single sentence while mundane segments get verbose treatment. OST=1 allocated to flat dialogue while the actual climax gets narration overlay (OST=0). Narration lacks intensifying language at peak moments.

**Measurement:** LLM Judge -- Evaluate against Section 1b rubric. Script is compared against a reference "excitement curve" derived from original subtitle content (climax density map).

---

#### E5: OST分配合理性 (OST Allocation) (High -- Code + LLM Judge)

**PASS:** OST=1 (OriginalSound) segments comprise 20-40% of total script time (targeting 30% per Section 1b convention). Each OST=1 segment is 3-8 seconds long. OST=1 segments are distributed across the full video (not clustered in one section). OST=1 is assigned to emotional peaks, key dialogue, climax moments, and suspense points. OST=0 (narration) covers exposition and connective tissue.

**FAIL (Code-detectable):** OST=1 proportion outside 10-50% range (hard outlier). Any OST=1 segment shorter than 2 seconds or longer than 12 seconds. Fewer than 3 OST=1 segments in a 15-clip script (under-distributed). OST=1 segments all in first or last 30 seconds of timeline (clustered).

**FAIL (LLM Judge-detectable):** OST=1 assigned to flat exposition where narration would serve better. OST=0 covers a key emotional outburst that should have been preserved as original sound. The OST allocation pattern does not follow emotional contour of the drama.

**Measurement:** Code -- Rust integration test computes OST ratio from parsed script, checks segment length and distribution. LLM Judge -- evaluates assignment appropriateness per emotional context of each segment.

---

#### E6: 叙事连贯性 (Narrative Coherence) (High -- LLM Judge)

**PASS:** Script follows strict chronological order matching the original drama timeline. All causal chains are complete: event A -> reaction B -> consequence C are all present. Temporal transition words connect segments naturally ("而这时", "没想到", "就在这时", "没多久"). A viewer who has not seen the original can follow the complete story from the narration alone. No "jump cuts" in narrative logic.

**FAIL:** Segments jump between time points without transition or explanation. Key causal links are missing (viewer sees a result but not its cause). The compressed timeline (1/3 of original duration) sacrifices cause-effect relationships in favor of preserving dramatic moments. Viewers report needing to rewatch segments to understand the plot. Temporal ordering errors (later event narrated before earlier event).

**Measurement:** LLM Judge -- Evaluate causal chain completeness and temporal ordering. Script is compared against a reference plot outline derived from original subtitles.

---

#### E7: 语言风格 (Narration Voice) (Medium -- LLM Judge)

**PASS:** Narration is colloquial and personal, not formal. Sentences are short (average <= 15 characters per sentence). Includes God-view perspective analysis ("她不知道的是...", "殊不知..."). Includes character psychology description ("主角此刻内心是崩溃的"). Has identifiable narrator personality (humorous, sarcastic, dramatic -- consistent throughout). Includes occasional opinion/commentary ("这操作真是绝了", "编剧的脑洞我服了"). Reads like a person telling a story, not an AI reading a script.

**FAIL:** Written-language vocabulary dominates ("综上所述", "然而", "极其", "进而"). No narrator personality or opinion. Pure factual retelling without perspective. Long, complex sentence structures. No character psychology. Flat, neutral tone throughout. Section 1b description: "观众评价为'AI念稿'或'机器人解说'."

**Measurement:** LLM Judge -- Evaluate against Section 1b rubric. Key signal: "Would a viewer know this was AI-generated within 5 seconds?" If yes, FAIL.

### 5.4 Eval Tooling Selection

**Tool scan result:** No existing eval tooling detected in the codebase (grep for langfuse, langsmith, arize, phoenix, braintrust, promptfoo, ragas returned zero matches across all `.py`, `.ts`, `.toml`, `.json` files).

**Selection rationale:** This is a Rust CLI/library running on the creator's desktop, not a cloud service. Standard Python-based eval platforms (Arize Phoenix, Langfuse, RAGAS, Braintrust) are not applicable because:
- No HTTP service to attach middleware/tracing to
- No Python runtime dependency
- No cloud deployment requiring external observability
- Single-user desktop application where eval is developer-driven, not operations-driven

**Selected approach for each eval concern:**

| Concern | Tool | Rationale |
|---------|------|-----------|
| Code-based structural checks | Rust `#[tokio::test]` integration tests | Native to the project. Uses `tempfile` + `wiremock` (already in Cargo.toml dev-dependencies). Zero external dependencies. |
| JSON repair validation | Rust `#[test]` unit tests on `repair_json()` | Covers all 6 repair strategies with known-bad JSON inputs. Fast, deterministic, no network calls. |
| Subjective quality (5 domain dimensions) | Python script calling OpenAI-compatible API | LLM-as-judge is the only practical approach for subjective dimensions. Python chosen for rapid iteration of judge prompts. Script at `scripts/eval/sde_quality_judge.py`. |
| Structural quality verification | Rust integration test + `validate_script()` | Phase 5 function reused per D-24. Tests overlap detection, field presence, format validation. |
| Prompt regression testing | Manual + LLM Judge before prompt changes | Prompt changes are infrequent (Phase 4 versioned prompts). Before deploying a new prompt version, run LLM Judge on reference dataset and compare scores to previous version. |

**Not selected (with rationale):**
- **Promptfoo:** Would require building a CLI harness for the SDE pipeline. Useful in future if CI/CD regression testing becomes frequent, but over-engineering for Phase 7 scope. Add when Phase 8 (SDP) introduces a second consumer of the same prompt infrastructure.
- **Arize Phoenix / Langfuse:** Python tracing tools incompatible with Rust binary. Add if Tauri frontend (Phase 10) introduces HTTP API layer with middleware tracing.
- **RAGAS:** Designed for retrieval-augmented generation. SDE is pure text generation without retrieval, so RAGAS metrics (faithfulness, context precision) are not applicable.

## 6. Guardrails

### 6.1 Online Guardrails (Runtime, Every Pipeline Execution)

These guardrails run during every `run_sde()` call. Since this is an internal desktop tool (not a user-facing SaaS), "online" means synchronous checks in the pipeline that prevent downstream waste. Each guardrail is fast (milliseconds, no additional API calls).

| # | Guardrail | Location in Pipeline | Failure Response | Latency Impact | Rationale (from Section 1 failure modes) |
|---|-----------|---------------------|------------------|----------------|-------------------------------------------|
| G1 | JSON Parse Guard | `script_gen.rs` after `step_generate_script()` | Abort pipeline. Save `narration_raw.json` for debugging. Return `SdeError::JsonRepair`. | < 5ms (in-memory) | Failure Mode 1: corrupted JSON wastes entire video processing. Gate before TTS generation. |
| G2 | Timestamp Non-Overlap Guard | `pipeline.rs` after `parse_script()` | Abort pipeline. Log which segments overlap. Return `SdeError::Validation`. | < 5ms (O(n) scan) | Failure Mode 3: overlapping timestamps produce corrupted video output. Gate before TTS generation. |
| G3 | OST Ratio Warning | `pipeline.rs` after `parse_script()` | Log `tracing::warn!` if OST=1 ratio outside 10-50%. Continue pipeline. | < 1ms | Failure Mode 2: not catastrophic (video still produces), but quality signal for creator. |
| G4 | Encoding Detection Fallback Chain | `subtitle.rs` in `step_parse_subtitle()` | Try UTF-8 -> UTF-16 -> GBK -> GB2312. If all fail, return `SdeError::ParseSubtitle`. | < 10ms (CPU-bound, in spawn_blocking) | Failure Mode 4: encoding failure prevents any output. Every encoding must be exhausted before giving up. |
| G5 | Empty Script Guard | `pipeline.rs` after `parse_script()` | If `clips.is_empty()` after per-item parsing, abort with `SdeError::ScriptGeneration`. | < 1ms | The LLM returned valid JSON but with no usable clips. Re-prompting would likely repeat. Fail-fast. |
| G6 | Runtime Duration Guard | `pipeline.rs` in orchestrator | If total step time > 30 minutes, log warning with breakdown. | Zero (passive timer) | Video processing can take 10-30 min. A duration outlier signals FFmpeg issues or resource contention. |

**Design principle:** Guardrails G1, G2, G5 are hard gates (abort pipeline). G3 is a soft warning. G4 is a retry mechanism (fallback chain, no additional API calls). G6 is a diagnostic timer.

**Rationale for keeping guardrails minimal:** Each guardrail adds either zero API cost (code-based) or trivial CPU time. The critical distinction is between "structural failure that wastes compute" (G1, G2, G5 -> abort) vs. "quality concern" (G3 -> warn).

### 6.2 Offline Flywheel (Batch, Quality Feedback Loop)

These run outside the pipeline on sampled outputs. They feed the improvement loop for prompt templates and LLM configuration.

| # | Flywheel Metric | Frequency | Action Trigger | Feedback Loop |
|---|-----------------|-----------|----------------|---------------|
| F1 | JSON Parse Failure Rate | Every 50 runs | If > 10% failure rate: review prompt template JSON formatting instructions; check LLM model's JSON reliability | Adjust `script_generation` prompt examples and format constraints |
| F2 | OST Ratio Distribution Trend | Every 50 runs | If mean OST=1 ratio drifts > 5% from baseline (30%): review prompt OST instructions | Adjust OST distribution guidance in prompt |
| F3 | LLM Judge Score Trend (all 5 quality dimensions) | Weekly batch of 10 random scripts | Any dimension drops > 0.5 from baseline: investigate prompt changes or model degradation | Re-calibrate prompt; consider model change |
| F4 | Encoding Detection Failure Rate | Every 50 runs | If > 5% failure: expand encoding detection chain; check for rare encodings in user base | Add more encoding variants to detection chain |
| F5 | Human Review Score Correlation with LLM Judge | Every 2 weeks, 10-sample holdout | If correlation < 0.7: recalibrate LLM Judge prompt; if still < 0.6 after 3 attempts, use human-only eval | Adjust judge system prompt and calibration examples |
| F6 | Pipeline Duration Outlier Rate | Every 50 runs | If > 5% of runs exceed 20 minutes: check FFmpeg configuration, hardware acceleration, or resource contention | Investigate individual outliers; adjust configuration defaults |

**Implementation:** Flywheel metrics are stored as structured JSON records in `output/sde/metrics/pipeline_metrics.jsonl` (append-only log). A weekly analysis script reads the log and generates a report:

```bash
# Weekly quality report
python scripts/eval/flywheel_report.py \
  --metrics output/sde/metrics/pipeline_metrics.jsonl \
  --scores output/sde/llm_judge/scores.jsonl \
  --output output/sde/reports/weekly_$(date +%Y%m%d).md
```

## 7. Production Monitoring

### 7.1 Monitoring Architecture

This is a desktop CLI/library -- there is no "production server" to monitor. "Production monitoring" means:
1. Structured logs at key decision points in the pipeline for post-hoc analysis
2. Metric collection in append-only JSONL files for trend analysis
3. Sampling strategy for human quality review

The project already uses the `tracing` crate (v0.1.44, listed in Cargo.toml). All monitoring builds on `tracing` with structured JSON formatting for machine parsability.

### 7.2 Tracing Setup

```rust
// In src/sde/pipeline.rs -- tracing events at each pipeline step

use tracing::{info, warn, error, instrument};

/// Run SDE pipeline with structured tracing at every step
#[instrument(skip(request, config, proxy, registry, prompt_manager),
             fields(task_id = %request.task_id, drama_name = %request.drama_name))]
pub async fn run_sde(
    request: SdeRequest,
    config: &AppConfig,
    proxy: Option<&ProxySection>,
    registry: &Registry,
    prompt_manager: &PromptManager,
) -> Result<PathBuf, SdeError> {
    let start = std::time::Instant::now();
    info!("SDE 流水线开始", task_id = %request.task_id, drama_name = %request.drama_name);

    // Step 0: Parse subtitle
    let step_start = Instant::now();
    step_parse_subtitle(state, &request.subtitle_path).await?;
    info!(target: "sde_pipeline", "字幕解析完成", duration_ms = %step_start.elapsed().as_millis(),
          segments = %state.subtitle_segments.len(), encoding = %state.detected_encoding);

    // Step 2a: Plot analysis
    let step_start = Instant::now();
    step_analyze_plot(state, &state.subtitle_text, provider, prompt_manager, request.temperature).await?;
    info!(target: "sde_pipeline", "剧情分析完成", duration_ms = %step_start.elapsed().as_millis(),
          analysis_length = %state.plot_analysis.len());

    // Step 2b: Script generation
    let step_start = Instant::now();
    step_generate_script(state, provider, prompt_manager, request.temperature).await?;
    info!(target: "sde_pipeline", "脚本生成完成", duration_ms = %step_start.elapsed().as_millis(),
          raw_json_length = %state.narration_raw.len());

    // JSON parse result
    match parse_script(&state.narration_raw) {
        Ok(script) => {
            let ost1_count = script.iter().filter(|c| c.ost == OstType::OriginalSound).count();
            let ost1_ratio = ost1_count as f64 / script.len() as f64;
            info!(target: "sde_pipeline", "脚本解析成功", clips = %script.len(),
                  ost1_ratio = %format!("{:.2}", ost1_ratio),
                  overlap_count = %detect_timestamp_overlaps(&script));
            state.script = script;
        }
        Err(e) => {
            error!(target: "sde_pipeline", "脚本解析失败", error = %e);
            return Err(e);
        }
    }

    // ... video processing steps (TTS, clip, merge, concat, composite) ...

    let total_duration = start.elapsed();
    info!(target: "sde_pipeline", "SDE 流水线完成", total_duration_ms = %total_duration.as_millis(),
          output_path = %output_path.display());
    Ok(output_path)
}
```

### 7.4 Sampling Strategy for Human Review

| Phase | Sample Rate | Method |
|-------|-------------|--------|
| First 20 runs (initial quality validation) | 100% | Manually review every output script. Score all 7 dimensions per Section 5.2 rubrics. |
| Weeks 1-4 (burn-in) | 20% | Review 1 in 5 outputs. Compare LLM Judge scores to human scores weekly. |
| Steady state (week 5+) | 10% or 2/week (whichever is larger) | Random sampling of completed tasks. Prioritize scripts where pipeline warnings were emitted (G3 OST warning, G6 duration anomaly). |
| After any prompt change | 100% of first 10 runs | Full manual review to catch regressions introduced by prompt modifications. |
| After JSON repair rate spike (flywheel alert) | 50% of next 20 runs | Focus on understanding why repair strategies are failing. |

### 7.5 Data Retention

- Pipeline metrics JSONL: retained indefinitely (append-only, ~1KB per run, ~10MB/year at 10,000 runs)
- Intermediate artifacts in `task_dir/`: retained until creator manually cleans (by design per D-17, to support debugging and manual script recovery)
- Reference dataset scores: versioned alongside prompt templates in `src/prompt/templates/short_drama_narration/eval_results/` (git-tracked, to correlate prompt versions with quality scores)
